# Architecture

## 架构目标

Turalk 的首个版本使用模块化单体：Web、Admin 与 API 分开部署，API 内部按业务域拆分模块，共享一个 PostgreSQL 实例。这个方案比一开始拆微服务更容易保证事务一致性、降低运维成本，也足以支持早期产品快速迭代。

模块化单体不等于无边界单体。每个 NestJS 模块拥有明确职责，跨模块调用应通过公开 service 或领域事件，避免任意访问其他模块内部实现。共享包只承载稳定的类型、配置和无业务状态工具，不承载业务规则。

## 运行时组件

- **Web**：Next.js 公共社区，负责公开页面、用户交互和服务端渲染。
- **Admin**：独立 React 应用，负责举报、审核、风控和审计操作；必须使用独立认证与授权策略。
- **API**：NestJS 模块化单体，负责业务规则、权限校验、事务和外部服务编排。
- **PostgreSQL**：事实数据源，保存用户公开主体、内容、举报、审核与审计记录。实名数据需要逻辑和权限隔离。
- **Redis**：缓存、限流、短期会话数据和未来的任务队列协调；不能作为关键数据的唯一存储。
- **OpenSearch**：帖子与评论的可搜索副本，数据由异步索引流程写入，不能取代 PostgreSQL。
- **对象存储**：后续保存头像和社区媒体。数据库只保存对象键和元数据，上传应使用短期签名 URL，并执行类型、大小与安全检查。

## 数据与调用方向

客户端只能通过 API 操作业务数据。API 在 PostgreSQL 事务完成后，通过可靠事件或 outbox 更新 Redis、OpenSearch 与异步任务。搜索结果返回内容 ID，最终可见性与权限仍由 API 和 PostgreSQL 状态确认。

## 未来拆分路径

当团队规模、吞吐量或隔离要求形成真实压力时，按边界逐步拆分，而不是整体重写：

1. 优先将通知、搜索索引和媒体处理拆为异步 worker。
2. 将 identity 拆为高安全等级服务，使用独立数据库、密钥和访问网络。
3. 将 moderation 与 audit 拆为治理域，消费内容和举报事件。
4. 根据负载再拆 auth、forum content 等核心服务。

拆分前需要先建立稳定模块 API、事件版本、幂等处理、outbox、分布式追踪和服务级指标。数据库表只有在服务所有权明确后再物理拆分，避免过早引入分布式事务。
