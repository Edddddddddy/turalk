# Security and Compliance

## 核心原则

1. **后台实名，前台匿名**：公开用户 ID、昵称、头像与实名记录分离，任何公共接口都不得返回实名字段。
2. **不保存身份证明文**：只保存不可逆 hash、认证提供商的不可读 token 或最小必要状态。日志、测试数据和分析系统同样禁止记录身份证明文。
3. **实名数据隔离**：identity 模块使用独立访问接口。未来应迁移到独立数据库、加密密钥、网络边界和更严格的备份策略。
4. **默认拒绝访问**：普通管理员默认不能查看实名信息。确有合规需要时采用细粒度权限、双人审批、限时授权和完整审计。
5. **敏感操作审计**：身份状态变更、管理员授权、内容处置、用户封禁和敏感数据访问必须写入 AuditLog。审计记录应防篡改并限制删除。
6. **最小化收集与保留**：只收集业务和法律要求所需的数据，定义保留期限与删除流程。

## 社区治理

项目不采用机械敏感词列表直接拦截正常发布，因为简单字符串匹配容易误伤语境，也不能替代治理责任。这不代表放弃内容安全：系统将提供用户举报、风险信号、人工复核、分级处置、申诉和审计能力，并依法及时处置违法内容。

风险规则必须可解释、可回溯和可调整。自动信号只能辅助排序与升级，关键处罚由有权限的人员复核。所有治理接口需要身份认证、最小权限、速率限制和幂等保护。

## 工程要求

- 密钥只通过环境变量或密钥管理服务注入，不提交 `.env`。
- 密码使用 Argon2id 自适应哈希；应用 pepper 在哈希服务内统一处理，pepper 不进入数据库或版本控制。
- refresh token 只保存 keyed hash，token 轮换后旧值失效；access/refresh JWT 使用不同 secret。
- JWT secret 和 `PASSWORD_HASH_PEPPER` 只通过环境变量或密钥管理服务注入，绝不提交真实值。
- 登录失败统一返回模糊错误，不透露邮箱是否存在、密码是否错误或账号具体状态。
- `register`、`login`、`refresh` 当前使用单实例内存限流，配置来自环境变量；生产环境仍需要 Redis、网关或边缘层限流，避免多实例绕过。
- 限流错误使用统一 envelope 和 `RATE_LIMITED` 业务码，不返回内部计数器或用户状态。
- Web 端当前使用 `localStorage` 临时保存 access/refresh token，仅作为开发阶段 MVP；该方案会受到 XSS 影响，生产环境应迁移到 httpOnly secure cookie、`Secure`、`SameSite`、CSRF 防护或更严格的服务端 session。
- 前端不得采集身份证号、身份证照片或其他实名原文；实名认证页在接入 provider 前只展示说明，不提供证件输入框。
- 当前 identity mock provider 只生成非 PII 的 provider token 和 hash，用于开发联调；这些字段不得返回前端或普通管理员视图。
- 真实 identity provider 接入前必须补充回调验签、幂等处理、provider 响应脱敏、独立权限和独立审计。
- provider token 和其他必要敏感字段需要应用层加密。
- API 对输入执行白名单验证，对输出使用显式 DTO，避免意外字段泄漏。
- 日志进行字段级脱敏，禁止记录凭据、证件信息、完整 token 和未脱敏请求体。
- 上线前完成威胁建模、权限测试、依赖扫描、备份恢复演练和适用法律审查。

本文档是工程原则，不构成法律意见。真实实名认证上线前必须由合格的法律与安全人员评审数据处理流程。
